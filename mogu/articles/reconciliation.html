웹훅 조회 앞당김의 복구 지연과 PG 호출 비용

주기 조회를 유지하면서 웹훅으로 조회 시각을 앞당긴 선행 비교다. 조회 주기·알림 조건별 결과이며, 이후의 작업 선점·만료 배치 효과와 합산하지 않는다. 현재 선택과 구매 결과

웹훅은 승인된 결제를 빨리 발견하는 데 도움이 됐지만, 알림을 놓친 거래까지 빠르게 복구해 주지는 않았다. 모구시장의 결제 접수 API는 202로 비동기 처리 시작을 알리며, 앱이 PG 승인을 확인할 때까지 예약 재고는 미확정 결제에 묶인다. 이 시간을 줄이려고 웹훅 수신 시 조회를 앞당기되 주기 조회는 유지했고, 조회 주기와 알림 유실·지연을 바꾸며 확정 지연과 PG 호출 비용을 비교했다. PG 중단 중에도 신규 요청이 계속되는 조건은 별도 시험으로 구분했다.

웹훅으로 조회를 앞당기면 승인 사실을 더 빨리 확인할 수 있지만, 알림이 유실된 거래는 여전히 주기 조회를 기다려야 한다. 실제로 500ms 주기·알림 유실 20% 조건에서 복구 중앙값은 약 0.63초에서 0.16초로 줄었지만 p99는 양쪽 모두 약 1.03초였으므로, 조회를 늘리는 비용과 지연 분포의 차이를 함께 비교했다.

웹훅은 사실의 권위가 아니라 영속 조회를 깨우는 신호다.

비교 대상은 승인·조회·취소 규칙, 워커 4개, PG 장애 입력이 같다. 정상 구매는 승인 조회로 복구하며 적체를 줄이기 위한 자동 취소는 수행하지 않는다. 비교 지표에는 p95·p99·최장 지연, 미해결 거래 수, PG 호출량, 미확정 재고 점유 시간을 포함했다.

웹훅 수신 시 PG 조회 일정 갱신

재고와 사용자 의사는 MySQL에, 승인·취소 사실은 별도 HTTP PG에 있다. 앱은 외부 호출 전에 attempt와 동일 멱등키의 operation을 영속화하며, ARMED 뒤 결과를 잃은 거래는 일반 예약 만료로 재고를 반환하지 않는다. 조회 결과가 올바른 paymentKey·orderId·금액·통화·상점·카드 수단에 연결될 때만 정상 구매를 확정한다.

기준 구현도 웹훅을 인증하고 inbox에 저장한 뒤 ACK하며, 알림이 오면 dirty 세대를 증가시켜 처리 중 도착한 이벤트를 다음 조회에 반영한다. 이 경로에서는 종결 거래의 외부 상태 변경도 확인한다. 개선 구현에서는 이 처리에 next_at을 현재 시각의 100ms 이후로 앞당기는 UPDATE를 추가했으므로, 두 구현의 차이는 웹훅 수신 여부가 아니라 조회 일정의 변경이다. 알림이 유실될 때 사용하는 영속 주기 조회는 두 구현 모두 유지한다.

-- 인증·거래 결합 검사, guard/예약/시도 잠금 뒤
INSERT inbox(...);                     -- 중복은 fingerprint로 합류
UPDATE attempts SET dirty=dirty+1 ...;
-- 웹훅 수신 시 다음 조회 앞당김
UPDATE attempts SET next_at=LEAST(next_at,
  TIMESTAMPADD(MICROSECOND,100000,UTC_TIMESTAMP(6))) WHERE id=?;
COMMIT;                               -- 이 다음에만 ACK

worker: durable claim → HTTP QUERY → 검증 → 구매/필요한 취소
missing webhook: 동일한 due 조회 안전망으로 재확인

웹훅에는 지연·중복·순서 역전이 있을 수 있으므로 알림의 상태를 그대로 DB에 반영하지 않고 인증된 PG 조회로 다시 확인하며, 조회를 수행한 워커의 generation이 현재 소유권과 일치할 때만 내부 상태를 갱신한다. 이미 전송된 외부 HTTP는 DB fencing으로 취소할 수 없다.

조회 주기·알림 지연·유실률별 반복 비교

k6로 초당 20 iteration을 20초간 워밍업한 뒤 60초간 측정하되, 예정 조회와 조회 앞당김의 실행 순서를 교대하며 각 조건을 독립 3회 반복했다. 한 iteration에서 예약·테스트 PG 인증 준비·앱 결제 접수·최대 5초의 상태 확인을 수행하므로 HTTP 요청률은 초당 20건보다 높다. 측정 뒤에는 최대 180초 동안 잔여 처리를 관찰하고 원장을 대조했다. 아래 표에는 입력 거래 중 실제 구매 수와 시작하지 못한 iteration을 별도로 표시했다.

PG 승인 효과는 0.3~1.0초의 결정적 지연 분포로 적용하고 승인 응답의 20%를 유실시켰다. apply_delay는 시뮬레이터가 연산을 영속화한 뒤 효과를 적용하기까지의 지연을 뜻하며, HTTP 연결을 그만큼 유지하는 설정은 아니다. drop_confirm은 응답 연결을 닫으므로 모든 거래가 HTTP timeout 800ms를 소비하지도 않는다. 비교 조건에서는 웹훅 유실률과 추가 전달 지연만 변경했다.

조회 주기에 따른 p99와 PG 호출 수 변화

조회 주기를 짧게 잡는 것만으로 꼬리 지연이 줄지는 않았다. 예정 조회만 사용하는 구현의 복구 p99는 500ms 조건에서 약 1.03~1.04초, 1000ms 조건에서는 약 0.76초로 오히려 긴 주기 쪽이 짧았다. 이 차이는 finish()가 첫 확인 뒤 pollMs, 다음 확인 뒤 2×pollMs, 이후 최대 4×pollMs를 기다리는 방식과 관련이 있다. 500ms에 조회했을 때 아직 승인 효과가 없다면 다음 조회까지 다시 기다려야 하는 반면, 첫 조회가 1초라면 이번 0.3~1.0초 지연 분포의 대부분을 한 번에 확인할 수 있다.

이를 확인하려고 PG config.apply_delay와 실제 승인 효과·조회 시각을 결합해 아래 표로 정리했으며, 효과 전 조회는 CONFIRM 효과가 발생하기 전에 실행된 QUERY를 뜻한다. 거래 수와 호출 수는 세 반복을 합산했고 p99는 실행별 범위로 표시했다. 기준 구현도 dirty 신호와 종결 거래의 재확인을 처리하므로 모든 조회가 고정 간격으로 실행되지는 않는다. 이 결과는 해당 PG 지연 분포와 backoff의 상호작용이며, 다른 지연 분포에서도 1초가 최적인지는 별도 측정이 필요하다.

재고 점유 시간의 측정 시작점 오류와 재계산

재고 점유 비용은 결제 응답이 아니라 예약 생성부터 계산해야 했다. 이전 Python 측정의 stock_seconds는 앱 결제 접수 응답 이후부터 구매 확정까지만 재어 예약 생성·인증·결제 접수 시간을 빠뜨렸으므로, 전체 재고 점유를 나타내지 못했다. 이를 바로잡기 위해 최초 결과와 거래 원장에서 DB created_at→terminal_at의 전체 미확정 점유와 attempt.started_at→terminal_at의 결제 중 점유를 따로 재계산했다.

전체 미확정 점유(item·s)
  = Σ(예약 terminal_at − 예약 created_at)
결제 중 점유(item·s)
  = Σ(예약 terminal_at − 결제 attempt.started_at)
관측 창 내 점유(item·s)
  = Σ(min(terminal_at, 관측 종료) − 예약 created_at)
  미종결 거래도 관측 종료까지의 시간을 더하고 censored 수를 남긴다.

구매 확정은 미확정 점유의 끝이지, 구매한 재고가 다시 판매 가능해지는 시점이 아니다. DB created_at은 논리적인 생성 시각이며 물리 디스크 커밋 순간의 정밀 타임스탬프가 아니다. 실제 카드 소유자 인증에 걸리는 시간도 시뮬레이터의 짧은 인증 준비와 다르다.

신규 요청이 계속되는 상황에서 PG 장애와 복구

단일 행과 16버킷에 10→40→100→10 iteration/s의 혼합 입력을 각 30초간 보내고, 행동은 HELD 취소 25%, 15초 TTL 만료 25%, 결제 시도 50%로 배정했다. 70초 시점부터 25초 동안 PG 업무 HTTP에 503을 주되 새 예약과 테스트 인증 준비는 계속된다. 이렇게 해야 단순히 발생기의 인증 요청이 멈춰 backlog가 생기지 않는 시험과 구분할 수 있다.

미확정 결제가 256건에 도달하면 신규 결제 접수는 거절하되, 이미 승인 결과를 기다리는 거래는 유지한다. PG가 회복되면 동일한 시도·키로 조회해 구매 의사 CONTINUE인 거래를 구매로 확정한다. 예약 수락이나 202 응답은 구매 수에 포함하지 않았다. 초기 혼합 하네스는 결제 pending이 없어지면 관찰을 끝내므로 마지막 15초 안에 생성한 HELD 예약은 아직 만료되지 않을 수 있어, 표에서는 이 잔여 예약을 별도로 표시했다. 워커·DB·PG 자원과 장기 보관 비용

두 구현은 워커 4개, 스캔 간격 50ms, HTTP timeout 800ms와 동일한 미확정 결제 상한을 사용한다. 조회 주기별로 비교하되 실제 PG 호출 수는 제한된 자원에서 발생한 결과로 측정했다. 같은 워커 수와 조회 주기를 사용해도 유효한 조기 조회가 추가되면 호출 횟수는 달라진다.

inbox에는 누적 10000건 상한이 있고, 상한에 도달하면 503을 반환하면서 영속 주기 조회를 계속한다. 이번 합성 시험은 수천 거래 규모로, 장기 보관과 아카이빙은 구현하지 않았다. Redis나 broker를 추가하더라도 PG 승인과 DB 구매 확정 사이의 상태 차이는 별도 조회·복구로 처리해야 한다.

실제 토스페이먼츠에는 테스트 키를 사용하는 어댑터와 UTF-8 원문 기반 HMAC 웹훅 검증을 구현했다. PG API를 직접 호출하는 계약 시험과 앱의 예약→카드 인증→결제 실행→조회→구매·취소를 연결하는 통합 시험을 구분했다. 실제 테스트 카드 인증과 앱 구매를 확인했으며, ARMED 이후 취소 의사를 수락한 거래의 PG 전액 취소·재고 반환도 확인했다. 실제 상점의 서명 없는 알림은 조회 전용 신호로 수신하고 저장 후 ACK 유실·재전송·인증된 PG 조회를 검증했다. 다만 실제 발신자 서명 검증은 완료하지 못했으며, 합성 서명 시험과 독립 HTTP PG 장애 시험으로 실제 상점의 서명 전달까지 검증한 것은 아니다. 실제 인증 뒤 발견한 mId 필드 결함과 수정은 실제 PG 통합 검증에서 설명한다.

측정 조건 상세: 조회 주기별 전원 상태

조회 1000ms의 기준 구현 3회차는 AC에서 Battery로 전원이 바뀌었고, 같은 조건의 조회 앞당김 3회차는 Battery에서 실행됐다. 앞선 250/500ms 조건은 AC, 이후 알림 지연·완전 유실 조건은 Battery였다. 따라서 조회 간격별 비교에는 전원과 실행 시점의 변동도 포함된다. 1000ms의 앞선 AC 두 반복에서도 꼬리 지연 감소가 관측됐지만, 개선 배율을 일반화하기보다 승인 효과 이전 조회 비율과 함께 해석했다.
