03 / EVIDENCE & REPRODUCTION

요청·DB·PG 원장을 대조하는 독립 감사

HTTP 응답이 성공했더라도 재고가 중복 배정되거나 PG 승인 없이 구매가 확정됐을 수 있다. 이를 확인하기 위해 요청 원장, MySQL 상태, 독립 PG 효과 원장을 대조했다. 장애 후 종결된 거래뿐 아니라 결과를 확정할 수 없어 수동 검토 상태(REVIEW)에 남긴 거래도 감사 대상에 포함했다.

검증 범위

실제 MySQL과 별도 HTTP PG 프로세스로 두 JVM의 경쟁, 프로세스 종료, DB 통신 중단과 지연 적용을 시험했다. 모두 한 노트북에서 수행한 로컬 장애 실험으로, 물리 고가용성이나 운영 규모의 최대 성능은 측정하지 않았다. 실제 테스트 카드의 앱 구매·취소와 서명 없는 웹훅 조회 신호·재전송은 별도의 소수 거래로 확인했다. 실제 발신자 서명 검증은 미완료다.

앱과 분리한 요청·DB·PG 감사

검증 하네스는 앱의 Java 클래스를 재사용하지 않는다. HTTP 요청을 자체 원장에 기록하고, MySQL의 읽기 전용 일관 스냅샷과 PG 관리자 읽기 API의 효과 원장을 수집한다. PG 제어·감사 API는 하네스 전용이며 앱의 Provider는 승인·조회·취소 API만 호출한다. 앱 응답이 구매 완료여도 대응하는 승인 효과가 없으면 감사가 실패한다. 다만 같은 macOS 사용자로 실행되는 로컬 프로세스이므로 운영 환경 수준의 보안 격리를 제공하지는 않는다.

판매 회차마다 초기 공급량 S가 판매 가능 수량 A, 예약·결제 진행 수량 H, 구매 수량 P의 합과 같은지 검사한다(S=A+H+P). H에는 HELD와 PAYMENT_PENDING, 결과 불명의 REVIEW·취소 진행 거래가 포함된다. 이와 함께 음수 가용량, 동일 사용자의 활성 예약·구매 중복, 사용자 guard의 소유자, 성공 응답에 대응하는 영속 예약, PG 효과에 대응하는 결제 시도, 승인·취소 효과 중복을 대조한다. 구매에는 승인 사실과 CONTINUE 의사가 있어야 하며, 승인된 거래의 조기 반환과 미확정 결제 상한 초과도 검사한다. 구매 이후 외부 취소처럼 지원 범위를 벗어난 변화는 구매 상태를 되돌리지 않고 REVIEW 사유로 남긴다.

요청 기록: 사용자 + 작업 + 키 + 본문 + HTTP/업무 결과 + 시각
앱 스냅샷: sales / reservations / guard / attempts / operations
            request_results / inbox / observations / budgets
PG 원장: payment / durable operation / effect / webhook / calls

정지점 감사:
  1. 신규 입력 중단
  2. 장애 회복 및 due 처리 기회 제공
  3. 해결된 결과와 의도된 REVIEW를 모두 설명
  4. 같은 실행의 원본·감사·코드 식별자를 연결

MySQL과 PG의 스냅샷을 원자적으로 읽을 수는 없다. 실행 도중 PG에는 DONE이지만 앱에는 pending인 순간이 존재할 수 있다. 실행 중에는 재고·사용자 제약의 안전성을 관측하고, 외부 효과와 최종 구매의 대응은 처리가 끝난 정지점에서 판정했다. 장기 장애에서는 종결 대신 미확정 사실의 보존과 자원 상한 준수 여부를 확인한다.

종결 거래의 외부 명령 차단과 결제 슬롯 갱신 검증

종결 거래의 외부 명령 허가를 검증하던 중, 수정 전 구현에서는 구매 후 늦은 웹훅과 조회 타임아웃이 추가 CONFIRM을 유발했다. 모든 비교군의 공통 외부 명령 허가 로직을 수정한 뒤, 구매·취소 종결 거래의 추가 CONFIRM/CANCEL은 0건이었다. 미종결 거래의 승인 복구와 이미 수락한 취소는 정상 수행됨을 함께 확인했다. 당시 구매 중심 독립 비교 · 수정 전후 호출 원장

  • 6개 비교군에 공통 정확성 회귀를 적용한 16개 실행
  • 단일 재고 행 · 실제 lease 만료 · 워커 직접 선점 · 커밋 직전 슬롯 검사: 외부 명령을 기록하는 operation 행의 잠금 대기 중 lease가 만료되면 추가 명령을 차단하고, 새 lease로 재선점한 뒤에는 구매가 완료되는지 확인했다.
  • 두 JVM의 전역 결제·웹훅 상한과 실패 시 롤백
  • 확장 복구 · 실패 경계 · 다중인스턴스 · 원래 재고 버킷 반환

종결 명령 차단의 회귀는 실제 PG 통합 시험과 분리해 로컬 HTTP 시뮬레이터에서 수행했다.

재시도와 한정 재고 후속 검증

현재 선택은 재시도·서버 대안의 구매 결과를 따른다. 공통 정확성 회귀 결과, 최종 장애·복구 회귀 결과, 최종 36회+한정 재고18회 원본 감사를 구분한다.

실제 MySQL·HTTP PG에서 종결 충돌의 영속 보존과 운영 조회, 소수 금액 거절, 명시적 503의 전체 롤백과 같은 키 재접수, 두 JVM의 전역 상한, 만료 배치의 커밋 직전 KILL과 재기동 반환, 결제·만료 잠금 경쟁을 확인했다. 이 정확성 결과와 400건/초의 낮은 구매 성공률은 별도로 평가했다. 수정 전후 근거

이 검증에서도 재고를 유지해야 하는 미확정 거래와 안전하게 반환할 수 있는 종결 거래를 구분했다.

실제 PG 응답 계약의 불일치와 수정 후 통합 검증

실제 테스트 카드 인증은 완료했다. 앱 예약→앱 결제 실행→PG 조회→내부 구매 확정도 확인했다. ARMED 이후 취소 의사와 실제 PG 전액 취소·안전 반환을 확인했다. 실제 상점의 서명 없는 알림을 조회 전용 신호로 수신했고, 저장 후 ACK 유실·재전송·인증된 PG 조회를 확인했다. 서명 없는 알림의 수신과 발신자 서명 검증은 다르다. 후자의 미확인 이유와 테스트 모드의 제한은 아래에서 설명한다.

실제 PG 응답의 상점 식별자는 mId인데 어댑터는 내부·시뮬레이터 필드인 mid로 읽고 있었다. 카드 인증과 PG 조회 200/IN_PROGRESS는 성공했지만 이 필드 불일치로 앱 승인 전에 중단됐다. 카드 인증 실패와 구분되는 구현 결함이다. 별도로 카드 인증 대기 만료도 관측했다. TTL이 지난 예약을 연장하거나 다른 주문에 재사용하지 않고 새 예약으로 재검증했다.

이 발견으로 HTTP 응답과 signed webhook 양쪽에 mId 경계 정규화를 추가했다. 원문을 변경해 HMAC을 확인하지 않으며, mId 누락·빈 값·충돌 별칭을 거절한다. 여섯 비교군에서 상점 식별자의 누락·빈 값·충돌을 검사하는 단위·거래 회귀가 통과했다. 수정 전 합성 fixture는 잘못된 mid 필드를 사용했으므로 HMAC·중복 동작의 근거이지 실제 Payment wire 계약 전체의 검증이 아니었다. 공식 Payment 객체 · 공식 웹훅 형식.

지원 결제수단을 검증할 때 앱은 PG 승인을 한 번 호출했고 독립 조회는 DONE을 확인했다. 그러나 실제 method는 간편결제였고 card 객체가 없었다. 지원하는 일반 카드 일시불 계약과 달라 내부 구매로 확정하지 않고 PAYMENT_PENDING/REVIEW와 재고를 유지했다. SDK의 method=CARD가 카드와 간편결제를 함께 열 수 있음을 공식 계약에서 확인한 뒤, 후속 인증 화면은 선택 카드사의 DIRECT·일시불 0으로 제한했다. 미지원 거래도 취소하거나 삭제하지 않고 원장에 남겼다. 응답 결합·수단 진단 · SDK 결제수단 계약

최초 120초 동안 inbox가 비어 있어 등록 여부를 개발자센터에서 추가 확인했다. 기존 테스트 웹훅 등록과 실제 DONE/CANCELED 이벤트는 존재했다. 수동 재전송에는 전송 ID·시각이 있었지만 서명 헤더가 없어 기본 앱이 401로 거절했다. 따라서 이 결과는 키 오류나 미등록 때문으로 볼 수 없다. 공식 문서는 HMAC 검증을 설명하지만 해당 체험 상점에서 서명이 생략된 이유는 확인하지 못했다. 실제 전송 헤더 진단 · 공식 이벤트 계약

테스트 실행에서는 TOSS_UNSIGNED_HINTS=test-query-only를 명시한 경우에 한해 서명 없는 요청을 조회 신호로 받는다. 기본값은 서명 필수이며 서명이 잘못된 요청은 예외 처리하지 않는다. 저장된 paymentKey·orderId·mId가 일치해야 하고 요청에서 임의 URL이나 새 결제를 만들 수 없다. DB에 영속화한 거래별 60초·전체 1초 간격, 앱 동시 진입 2개, inbox 누적 10000건 상한을 적용하고 여러 인스턴스도 같은 DB 예산을 공유한다. 이 제한은 악의적 조회 유도를 줄이기 위한 것이며 발신자 인증은 아니다. 예산 소진 시 429, 같은 원문에는 중복 ACK를 반환한다. 거래별 간격 안의 다른 본문은 저장 없이 성공 처리하지 않고 429로 재전송을 요청한다. 미해결 거래의 주기 조회도 계속 실행한다.

웹훅의 status·금액을 사실 판정에 사용하지 않고 이미 저장한 결제 키로 인증된 조회를 실행한 결과만 공통 검증에 보낸다. 거짓 취소·잘못된 금액·알 수 없는 키·상점 불일치·틀린 서명·재시작 후 제한과 공유 예산 rollback을 합성 공격 회귀에서 확인한다. 실제 상점 전달은 별도 재전송·ACK 유실 시험과 후속 독립 조회 감사로 구분한다. 조회 신호 제한을 보완한 뒤에는 거래별 cooldown의 다른 이벤트를 성공 ACK로 버리지 않고 429로 재시도를 요청한다. 실제 알림 재전송 시험은 저장한 동일 이벤트의 ACK 유실을 검증한 것이다. 다른 이벤트를 제한하는 응답 변경은 6개 비교군의 합성 회귀로 별도 확인했다. 서명된 실제 이벤트 수신은 검증하지 못했으며, 라이브 적용 전 해당 상점의 서명 지원 계약을 확인해야 한다.

거래별 검증 결과: 실패 원인과 수정 후 정상 경로

아래 목록은 서로 다른 테스트 거래의 결과다. 초기 거래에서 확인하지 못한 구매·취소·알림 전달은 후속 거래로 검증했으며, 서명된 실제 이벤트의 발신자 검증은 아직 완료하지 못했다.

  • 카드 인증 대기 만료: 카드 인증이 완료되지 않아 구매와 실제 웹훅 전달을 검증하지 못했다.
  • PG 응답 필드 오류: 카드 인증과 PG 조회는 성공했지만 상점 식별자 필드를 잘못 읽어 KeyError가 발생했다. 앱 구매와 실제 웹훅은 미검증 상태였다.
  • 미지원 결제수단의 승인: 카드 인증 뒤 결제 접수는 202였지만 지원 범위 밖의 간편결제여서 PAYMENT_PENDING에 남았다. 구매 검증은 AssertionError로 실패했고 취소 복구는 미검증, 실제 웹훅은 미수신이었다.
  • 정상 구매: 카드 인증과 결제 접수 202 이후 PURCHASED로 확정돼 구매 검증을 통과했다. 이 거래에서는 취소 복구를 시험하지 않았고 실제 웹훅도 수신하지 않았다.
  • 결제 진행 중 취소: 카드 인증과 결제 접수 202 이후 취소를 요청해 CANCELLED로 확정됐다. 취소 복구 검증은 통과했으며 이 거래의 실제 웹훅은 수신하지 않았다.

별도의 실제 PG·DB 감사에서는 구매·취소·미지원 REVIEW를 각각 대조하고 회차·버킷 재고 보존과 사용자 guard 해제를 확인했다. 실제 PG 내부 효과 원장은 제공되지 않아, 시뮬레이터처럼 승인 효과 개수를 독립 집계하는 검증은 수행하지 못했다. 별도 실제 PG·DB 감사

외부 PG의 원문 결제 키·주문 식별자는 로컬 비공개 자료에 보관했다. 공개 결과에는 합성 앱 예약 UUID·상태·HTTP 코드·금액 검증과 결제 키의 해시를 남기고 인증키·카드 정보·원문 결제 객체를 제외했다. 테스트 환경의 소수 거래이며 실제 과금과 실제 PG 부하 시험은 하지 않았다.

운영 조회와 수동 확인

운영 조회 API /ops/status는 pending·REVIEW의 경과 시간과 예산 사용량을 보여준다. /ops/reconcile은 사유, action ID와 예상 generation을 받아 같은 결제 시도의 조회를 다시 예약한다. 사용자 취소에는 원래 사용자 인증과 멱등키를 사용한다. 구매 상태나 재고를 직접 덮어쓰는 API는 제공하지 않는다. 이 절차는 로컬 복구 연습으로 검증했으며 실제 고객 장애 대응 이력은 아니다.

실패한 시험과 하네스 수정

장애 시험이 실패했을 때는 앱 결함과 하네스의 잘못된 가정을 구분했다. 자격정보 변경은 앱의 실행 차단 조건을 보완했고, DB 통신 중단과 풀 포화 시험은 실제 관측에 맞춰 판정 방법을 수정했다.

PG 접속 범위의 이름은 그대로 두고 인증키만 바꾸면 기존 시도의 결제를 다른 자격으로 실행할 수 있다. 이를 감지하도록 endpoint, 상점 범위와 인증키 지문을 영속화했다. 원래 키 값은 저장하지 않는다. 실제 인증키를 바꿔 JVM을 재기동한 뒤 실행 차단과 원래 자격 복원 후 복구를 확인했다.

웹훅 inbox 저장 중 DB를 pause한 시험에서는 9초 안에 HTTP 응답을 받지 못했다. 최초 하네스는 예상하지 않은 예외로 처리해 실패했다. 원본을 보존한 뒤, DB 저장 전 성공 ACK가 없었다는 통신 결과와 서버의 명시적 503을 구분하도록 판정을 수정했다. 클라이언트 timeout만으로 서버가 어떤 응답을 결정했는지는 알 수 없다. DB 회복 뒤에는 주기 조회로 구매가 확정됐다.

풀 포화 시험의 첫 시도는 정확히 12개의 예약 hook이 도착하기를 기다리다 실패했다. 만료·복구 작업도 같은 풀을 사용하므로 실제 점유 수를 그 수로 가정할 수 없었다. 수정 시험은 Actuator의 active connections=16을 직접 확인한 뒤 요청의 제한된 실패와 해제 후 회복을 검증했다. 판정 대상인 풀 포화는 유지하고, 불필요한 실행 순서 가정을 제거했다.

재고 분할·잠금 단축의 공통 장애 회귀

재고 버킷과 재고 잠금 구간 단축 구현에는 공통 거래·확장 장애·실패 경계 시험을 적용했다. 버킷 구조는 같은 멱등키의 다중 JVM 경쟁과 버킷별 재고 보존식도 검사했다. 재고 버킷 계약 감사 · 재고 버킷의 프로세스·DB 장애 · 버킷 간 할당량 이전을 제외한 시험 범위 · 잠금 단축 계약 감사

버킷은 sales.available의 과거 열 대신 bucket별 quota=available+HELD+PAYMENT_PENDING+PURCHASED와 회차 전체 합계를 검사한다. request_results의 성공 ID도 독립 입력 원장과 연결한다. 호스트 비용에서는 같은 Docker backend 이름의 PID들을 합하고, VM CPU를 사용할 때 guest DB cgroup을 다시 더하지 않는다.

재고 분할·웹훅·워커 직접 선점의 회귀

재고 분할·웹훅 조회 구조와 워커 직접 선점 구조에는 거래 계약, 확장 장애, 실패 경계, 다중 인스턴스, 버킷 보존과 Toss 형식 fixture를 각각 실행했다. 실제 PG 모드 앱에는 k6 부하를 보내지 못하도록 실행 전 검사도 확인했다. 잘못된 테스트 키와 빈 임시 스키마를 사용한 이 시험에서 외부 PG 호출은 0건이었다. 조합 계약 감사 · 워커 직접 선점의 프로세스·DB·과부하 회귀 · 다중 JVM 경쟁 · 버킷 보존 · preflight 시험

같은 노트북에서 어디까지 비교할 수 있는가

장비는 Apple M5, 10 논리 CPU, 메모리 16GiB다. Docker VM에 약 7.65GiB가 할당돼 있고, 앱·PG·발생기는 호스트 프로세스, MySQL은 컨테이너로 실행한다. DB에는 2CPU quota와 1GiB 메모리 제한을 두고 redo flush-at-commit=1, sync-binlog=1을 유지했다. 앱 heap은 384MiB, 워커는 4개다.

CPU quota를 적용했지만 전용 물리 코어를 할당한 환경은 아니다. CPU·메모리 대역폭·디스크·열 상태를 공유하며 DB cgroup만으로는 VM 전체 비용을 알 수 없다. OS·하드웨어·전원 상태와 함께 앱·PG·발생기의 CPU/RSS, DB cgroup의 누적 사용량을 기록했다. PG와 DB가 물리적으로 분리된 운영 환경의 성능은 이 결과로 판단할 수 없다.

일반 HTTP 부하는 k6 arrival-rate executor로 발생시키고, 사용할 VU가 없어 시작하지 못한 작업은 dropped_iterations로 기록한다. Python은 PG 장애 제어, 독립 감사와 근거 수집에 사용했다. 목표 도착률과 실제 시작 수를 구분하고 성공·품절·사용자 제한·입장 거절 429·오류의 지연을 각각 집계했다. 빠른 거절을 포함한 전체 p99와 구매 지연도 분리했다. 초기 예비 비교의 100개 거래는 PG 승인과 내부 구매가 모두 완료됐는지 감사한 뒤 집계했다.

계측 방법과 검증 한계

결과표와 그래프는 요청 원장, MySQL 스냅샷, 독립 PG 효과 원장과 자원 시계열을 대조해 계산했다. 초기 예비 시험과 후속 k6 측정은 입력 조건·계측 범위를 구분했으며, 과거 참고 자료의 부하 수치는 새 실험에 섞지 않았다.

별도 15초 JFR 진단도 보존했다. 이 실행은 프로파일러가 켜진 별도 run이며 비교 표에 섞지 않았다. ExecutionSample 수가 적어 특정 CPU 함수가 병목이라고 단정할 근거는 부족했다. 따라서 GC 옵션이나 직렬화 스택을 변경하지 않았다.

남은 검증 범위는 물리적으로 분리된 자원, 더 긴 장애와 반복 실행이다. 단일 호스트의 전원·실행 시점 변동은 통제하지 못했고, 장기 아카이빙·실서비스 인증·운영 모니터링 구성도 포함하지 않았다. 실제 PG 발신자 인증의 미확인 범위는 앞의 통합 검증 절에 정리했다.
