MOGU MARKET / BACKEND CASE STUDY

한정 재고 배정과 비동기 결제의 병목 개선

모구시장은 한정 수량의 상품을 예약하고 외부 PG를 통해 결제를 완료하는 공동구매 서비스다. 이 프로젝트에서는 인기 상품의 재고 행 경합을 줄여 예약을 더 많이 받아도, 결제 작업 대기와 만료 재고 반환이 뒤따르지 못하면 실제 구매는 그만큼 늘어나지 않는다는 점을 확인했다. 결제 슬롯이 가득 차 접수를 거절당한 예약 고객에게 제한 재시도를 허용하는 방법도 비교했지만, 전체 구매 결과를 기준으로는 서버의 작업 선점과 만료 처리를 개선하는 쪽을 선택했다.

대표 혼합 실험은 신규 사용자 100명/초와 400명/초를 각각 90초 동안 유입시키고, 예약 후 행동을 결제 50%·취소 25%·만료 대기 25%로 배정했다. 따라서 결제 대상은 반복당 4,500명·18,000명이며, 구매 기한 10초는 예약 요청 시작부터 센다. 아래의 1회 시도는 클라이언트의 결제 접수 정책을 뜻하며, 서버의 PG 조회·승인 복구 재시도는 계속 실행된다.

채택 구조: 선점 인덱스·만료 배치 / 1회 시도

클라이언트의 결제 접수를 한 번으로 유지하고 서버의 선점 인덱스와 만료 처리를 함께 바꾼 결과, 400건/초의 10초 내 구매는 평균 4,405명/18,000명으로 커밋 직전 슬롯 검사 구조보다 26.24% 증가했다. 같은 집계 시간창의 구매 1,000건당 전체 CPU도 303.54초에서 220.47초로 줄어, 더 많은 구매를 완료하면서 단위 처리 비용을 낮췄다. 다음 결제 작업을 고르는 쿼리에는 복합 인덱스를 적용했고, 만료 예약은 최대 32건씩 묶어 원래 재고 버킷별로 수량을 합산한 뒤 한 번에 커밋했다. 클라이언트의 제한 재시도는 기본 정책에서 제외했으며, 100건/초에서는 세 반복 모두 4,500명 전원이 기한 내 구매했다.

모든 결제 대상에 최초 요청 시작 후 10초라는 같은 관찰 기한을 적용해 독립 3회 측정한 결과, 기한 내 구매율은 100건/초 입력에서 평균 100.00%[100.00–100.00%], 400건/초에서 24.47%[23.91–24.76%]였다.

이 프로젝트에서는 예약·외부 HTTP 결제·구매 확정·취소·장애 복구를 새로 구현하고 로컬에서 검증했다. 재고 상태는 MySQL에서 관리하고 승인·취소 사실은 PG 응답과 조회로 확인하되, 과거 제품의 전체 기능이나 실서비스 규모까지 재현하지는 않았다. 예약 수락, 품절·과부하 거절, 결제 접수 202와 실제 구매 수를 분리해 측정했다.

개선 전후 아키텍처와 설계

단일 재고 행과 스케줄러 중심의 거래 처리

모구시장은 판매 회차별로 한정된 재고를 예약한 뒤 결제하는 서비스다. 기준 구현은 예약 시 MySQL 재고 행에 비관적 잠금을 획득하고, 재고 차감과 예약 생성을 하나의 트랜잭션으로 처리했다. 이 방식은 초과 판매를 방지하지만, 동일 회차의 예약이 한 행에 집중되므로 요청이 몰리면 잠금 경합이 발생했다. 결제 API는 요청을 영속화한 뒤 202를 반환하고, 스케줄러가 DB의 결제·복구 작업을 선점해 서버 내부 워커에 전달했다. 워커는 DB 트랜잭션 밖에서 PG 승인·조회 API를 호출하고, 응답의 주문 식별자와 금액을 검증한 뒤 구매를 확정했다. 승인 응답 유실은 결제 실패로 처리하지 않고 주기 조회로 대사했다. 만료된 예약은 잠금 후 결제 미접수 상태를 재확인해 건별 트랜잭션으로 재고를 반환했으며, 결제 진행 중이거나 승인 결과가 불명확한 거래는 예약 TTL만으로 재고를 반환하지 않았다.

재고 분산과 워커 직접 선점, 배치 반환을 적용한 거래 처리

개선 후에는 동일 회차의 재고를 같은 MySQL 안의 16개 행으로 분할해 행 잠금 경합을 분산했다. 사용자별 중복 예약·구매 제약은 회차 단위로 유지했다. 작업 배분은 스케줄러가 가용 워커를 실행하고, 각 워커가 DB에서 다음 결제·복구 작업을 직접 선점하는 구조로 변경했다. 선점 쿼리에는 실행 가능 여부와 예정 시각, 작업 ID 순서의 복합 인덱스를 적용해, 한 건을 선택할 때 발생하던 정렬과 불필요한 행 잠금을 줄였다. 웹훅은 PG 조회 시점을 앞당기는 신호로만 사용하고, 알림 유실에 대비한 주기 조회는 유지했다. 만료 처리는 잠금 후 예약 상태를 재검증한 뒤 원래 재고 행별로 반환 수량을 집계해 한 트랜잭션으로 반영함으로써 건별 커밋 비용을 줄였다. 배치가 여러 행의 잠금을 동시에 보유하는 만큼 잠금 순서와 배치 크기를 제어했으며, 결제가 진행 중이거나 결과가 불명확한 거래는 계속 반환 대상에서 제외했다.

구매 결과로 확인한 개선 효과

재고가 충분한 과부하 조건에서, 기한 내 구매 확정 건수를 26.24% 늘리면서 구매 1,000건당 호스트 CPU 시간을 27.37% 줄였다. 재고 분할과 워커 직접 선점이 이미 적용된 선행 구조 대비, 신규 사용자 400명/초에서 예약 시작 후 10초 내 구매가 평균 3,489.33건에서 4,405건으로 증가했고, 구매 1,000건당 CPU 시간은 303.54초에서 220.47초로 감소했다. 재고 정합성과 결제 복구 보장을 유지한 채, 제한된 단일 노트북 자원에서 더 많은 구매를 완료하고 단위 처리 비용을 낮췄다는 데 의미가 있다. 다만 이 부하에서 결제 대상의 10초 내 구매율은 24.47%였으므로, 400명/초를 안정적으로 처리하는 수준까지 도달한 것은 아니다.

관심사별 읽기 순서

  • 병목 분석과 최종 개선: 선점 인덱스·만료 배치 → 결제 슬롯과 트랜잭션 경계 → 혼합 부하의 적체
  • 재고 경합과 자원 제한: 단일 행 잠금과 재고 분할 → 동시 입장 제한 → 워커 작업 배분 → 지속 부하 비교
  • 결제 정합성과 장애 복구: 결과 불명과 재고 반환 → 종결 거래의 실행 허가 → 웹훅과 주기 조회 → 독립 감사·실제 PG 검증

문제별 상세 글

결제 접수 재시도의 한계와 선점 인덱스·만료 배치 개선

클라이언트의 제한 재시도를 제외하고 서버의 선점 인덱스와 만료 배치를 채택한 이유를 설명한다. 세 구조의 36회 본 측정과 한정 재고 18회 결과로, 같은 사용자 입력의 전체 구매 증감과 최초 결제 고객·재고 반환에 미친 영향을 비교한다.

종결 거래의 재승인 결함과 외부 명령 허가 검증

종결 거래의 추가 승인·취소 차단, PG 사실 충돌의 영속 보존, 소수 금액 오검증을 실제 MySQL 상태와 PG 호출 원장으로 검증한다.

요청·DB·PG 원장을 대조하는 독립 감사

정확성·장애 시험의 독립 감사 방법과 실제 PG 카드 인증·구매·취소·알림 검증의 완료 범위를 설명한다.

선행 비교: 결제 슬롯 포화의 원인과 트랜잭션 구조 비교

단일 재고 행, 워커 직접 선점, 커밋 직전 슬롯 검사를 독립 실행으로 비교하고, 당시의 15% 채택 기준에 따라 대안을 기각한 이유를 설명한다.

선행 비교: 혼합 부하에서 예약 수락과 구매 확정이 벌어진 원인

단계형 혼합 부하에서 예약 수락률과 구매 확정률이 벌어진 원인을 분석하고, 버킷과 행동이 연관됐던 입력이 결과 해석에 어떤 한계를 남겼는지 설명한다.

선행 비교: 지속 부하와 복구 비용으로 비교한 재고·워커 구조

충분한 재고의 지속 예약 부하와 PG 장애 복구를 비교해 재고 분할·워커 직접 선점을 선택한 당시 근거를 설명한다.

HTTP 연결 상한과 결제 작업 배분의 병목

워커가 남아 있어도 작업 배분이 늦으면 구매가 지연되는 원인을 살펴보고, HTTP 연결 상한의 영향을 분리한 뒤 워커가 직접 작업을 선점하도록 바꿨을 때의 이득과 유휴 조회 비용을 설명한다.

단일 재고 행의 잠금 경합과 16개 버킷 분할

단일 재고 행의 잠금 경합을 확인하고, 잠금 구간 단축과 같은 MySQL 안의 재고 행 분할을 구현·비교한다.

동시 입장 제한과 재고 분할 수에 따른 처리량·지연

동시 입장 제한과 버킷 수, 회차 분산, 품절·중복·편향 입력이 처리량에 미치는 영향과 부하 발생기 한계를 다룬다.

결제 결과 불명 상태의 복구와 재고 반환 조건

외부 호출 전 영속 실행 허가, 예약 TTL, 오래된 워커, 취소 의사와 승인 복구를 연결해 안전한 재고 반환 조건을 설명한다.

웹훅 조회 앞당김의 복구 지연과 PG 호출 비용

조회 주기와 웹훅의 지연·유실에 따른 복구 지연·PG 호출량을 비교하고, 재고 점유 지표의 측정 오류를 재계산한다.

최종 선택과 비교 결과

기존 대안 가운데 400건/초에서 구매 결과가 가장 좋았던 것은 커밋 직전 슬롯 검사 구조로, 평균 3,489.33명이 기한 내 구매했고 구매 1,000건당 CPU는 303.54초였다. 선점 인덱스·만료 배치 구조는 같은 재시도 정책을 적용한 두 기존 구조보다 나았으며, 최종 1회 시도 정책에서도 사전에 정한 구매·최초 결제 고객·비용·꼬리 지연 조건을 모두 충족했다. 다만 100건/초의 구매 1,000건당 CPU는 119.09초에서 127.39초로 6.97% 증가해, 사전 한도 10% 안이기는 해도 저부하 비용은 늘었다. 반면 제한 재시도는 처음 결제 접수를 거절당한 고객 중 평균 1,318.33명의 기한 내 구매를 가능하게 했지만, 전체 기한 내 구매는 4,405명에서 2,839명으로 1,566명 감소시켰고 최초 결제 고객의 구매 결과와 추가 비용 조건도 충족하지 못했다. 예산 사전 조회는 짧은 판별 실험에서 잠금 대기를 줄였지만 구매가 992명에서 720명으로 감소해 제외했다. 선점 인덱스 단독 구현은 중간 비교 대상으로 남겼으며 최종 조합의 전체 개선율을 단독 효과로 계산하지 않았다.

결제 거절·결과 불명·종결 충돌 처리

PAYMENT_ADMISSION_CLOSED는 결제 관련 쓰기가 모두 롤백된 명시적 거절이므로, 슬롯이 열린 뒤 같은 예약과 멱등키로 다시 접수할 수 있다. 반면 일반 DB 오류나 응답 유실은 저장 여부를 알 수 없어 조회와 영속 복구로 확인한다. 종결 거래에는 추가 승인·취소를 보내지 않으며, 인증된 PG 조회가 내부 종결 결과와 충돌하면 REVIEW로 보존해 일반 오류나 재조회, 재기동으로도 검토 사유가 사라지지 않게 했다. 호출 원장과 운영 조회

남은 한계

이처럼 개선 후에도 400건/초는 여전히 과부하로, 결제 대상의 24.47%만 10초 내 구매했고 성공 지연 p99 6.70초와 별개로 만료 반환 p99는 122.57초였다. 단일 JVM의 최대 32건·fixedDelay 200ms 반환은 처리 시간을 0으로 가정해도 초당 160건이 상한이며, 같은 90초 유입이 만든 만료 업무량은 이를 넘었다. 예약 시 결제 실행 슬롯까지 약속하는 계약으로 바꾸지는 않았다. 재고 3,000개 조건의 1회 시도에서는 기한 내 구매가 선점 인덱스·만료 배치 평균 2,873명, 커밋 직전 슬롯 검사 2,832.33명, 워커 직접 선점 2,834.33명으로 이득이 작았다. 이 결과는 노트북 한 대의 공유 CPU·VM·디스크에서 얻은 세 반복의 관측이므로, 실서비스 최대 성능·물리 HA·임의 부하에서의 기아 부재까지 판단할 수는 없다.

앱·MySQL VM·PG 시뮬레이터·k6·관찰기는 한 M5/16GiB 노트북과 디스크를 공유한다. 전체 호스트 CPU와 구매 분모의 시간창을 맞췄으며 VM 안의 DB CPU를 중복 합산하지 않았다.

실제 테스트 카드 인증·앱 구매·전액 취소·알림 재전송은 별도의 소수 거래로 확인했지만, 실제 발신자 서명 검증은 완료하지 못했다. 합성 부하는 독립 시뮬레이터에만 보냈으며, Redis 입장 제어와 Kafka 예약 큐는 구현하지 않아 성능 효과를 비교할 자료가 없다. 이들과 달리 만료 재고 반환의 DB 커밋 배치는 실제로 구현하고 비교했다.
