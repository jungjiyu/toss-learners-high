개선 후

개선 흐름과 검증 결과

개선 전은 과거 운영 서비스가 아니라 이번에 재구현한 기준 구조다. 서버는 HTTP 또는 WebSocket으로 받은 메시지의 인증·방 권한과 전송 키를 검사하고, 본문·방별 순번·중복 판별 기록·전달 작업을 하나의 MySQL 트랜잭션에 저장한 뒤 저장 완료를 응답한다. 별도 실행기가 전달 작업을 선점해 같은 서버의 방 구독자에게 팬아웃한다. 느린 수신자는 유한 버퍼에서 기다리고, 버퍼가 넘치거나 재접속하면 마지막 연속 cursor 이후를 DB에서 다시 읽는다. 이때 수신자마다 조회와 직렬화가 반복되고 소켓도 프레임마다 쓴다. 개선 과정의 부하 시험에서는 DB 왕복과 소켓 쓰기 비용을 확인했으며, 반복 재접속에서는 일반 사용자 자신의 재시도 대기와 동시 구독 조회가 수신 지연을 늘렸다.

개선 후에도 저장 트랜잭션과 commit 이후 응답은 유지했다. 전달 실행기는 여러 메시지의 선점·본문 조회·완료 기록을 묶고, 바로 보낼 수 있는 메시지는 즉시 팬아웃한다. 느리거나 누락이 있는 수신자는 별도 본문 버퍼를 쌓지 않고 공유 로그 조회로 전환한다. 같은 방의 인접 범위 조회를 병합하고, 권한·보관 경계·최신 순번·본문을 한 SELECT의 snapshot으로 읽어 DB 왕복을 줄였다. 불변 본문의 JSON과 UTF-8 길이는 유한 캐시에 보관하며, 연결별 writer는 이미 대기 중인 최대 8개 프레임을 추가 대기 없이 묶어 flush한다. 복구는 주기 확인뿐 아니라 적용 확인과 조회 완료에도 다음 작업을 깨운다. 마지막으로 서버의 초기 구독 권한·순번 조회를 한 SELECT로 줄이고, 실제 브라우저에는 안정 연결 후 첫 단절에만 빠른 무작위 재시도를 허용하되 반복 실패에는 대기를 늘렸다. 캐시·공유 작업의 관리 비용이 추가되지만 복구 원본은 MySQL에 남는다. 저장 응답·소켓 쓰기·클라이언트 원자 적용·읽음은 끝까지 별개로 취급한다.

성과는 전체 구조의 단일 전후 개선율이 아니라 변경 단계별로 검증했다. 조회·직렬화·소켓 쓰기를 함께 개선한 단계에서는 같은 601,000건의 수신 의무를 복구하는 독립 3회 비교에서 서버와 DB의 합산 CPU 시간 중앙값이 180.34초에서 140.52초로 약 22% 줄었다. 마지막 구독·재시도 개선은 같은 노트북과 자원 예산에서 500연결·HTTP 송신 45건/초·10분을 전후 각각 3회 비교했다. 인기 방 400연결 중 100개를 느리게 하고 전체 연결을 30초마다 재접속시켰을 때, 일반 방 송신 5,400건은 매회 모두 저장됐다. 그중 최초 전송 시작 후 250ms 안에 예정 수신자 모두에게 순서대로 도착한 비율은 95.46~98.19%에서 98.74~99.30%로 높아졌다. 이는 k6 메모리 수신이며 영속 적용 성능은 아니다. 느린 수신자의 회차 내 복구 실패가 남았고, 최종 반복 하나는 연결 실패 15회와 인기 방 송신 미확정 1건을 포함해 전체 저장 수락률이 94.82%로 목표 95%에 못 미쳤다. 따라서 이 조건에서 일반 사용자의 경험이 개선됐다는 결론이며, 모든 부하·복구 목표를 달성했다는 의미는 아니다.

CPU 수치는 중간 단계끼리의 동일 복구량 비교, 수신 비율은 직전 구현과 최종 구현의 비교입니다. 그림의 기준 구현과 최종 구현을 직접 측정한 하나의 개선율로 합치지 않았습니다.
