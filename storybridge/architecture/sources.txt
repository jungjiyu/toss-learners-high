2. 실제 활성 구성과 설정
두 그림 모두 단일 JVM 채팅 서버 + MySQL/InnoDB + 브라우저다.
HTTP SEND와 WebSocket SEND는 Store.send를 공유한다. 아래 성능 수치는 HTTP SEND다.
선정 소스의 Publisher는 Gateway.publish를 직접 호출한다. RabbitMQ/Redis/외부 캐시는 없다.
별도 분산 후보 C4의 broker·두 gateway 시험은 최종 선정 소스에 통합된 결과가 아니다.
방별 routes 인덱스와 별도 socket writer는 개선 전에도 존재했다. 새 개선처럼 표시하지 않았다.
두 그림의 저장·전달 실행기·복구·writer는 같은 서버 내부 기능이다. 별도 배포 서비스가 아니다.

3. 그림 화살표와 정합성 경계
정확한 커밋별 메서드 행 번호와 영구 GitHub 링크: code-map.json.
집계 원본에서 추출·재계산한 개별 수치와 원본 해시: numbers.json.
아래 파일명은 src/main/java/dev/storybridge/를 기준으로 한다.

[SEND → SEND 처리 / commit 후 STORED → 발신자]
Api.send 및 Gateway.send → Store.send. Auth.header/verify 또는 SocketConfig.beforeHandshake.
Store.authorize가 회원 방 권한 확인. room head FOR UPDATE 후 같은 sender/key receipt 조회.
같은 key/hash는 기존 receipt, 같은 key/다른 hash는 KEY_CONFLICT.
message + send_receipt + outbox INSERT와 room head 갱신은 하나의 write.execute.
TransactionTemplate가 commit을 마친 뒤 반환해야 STORED를 구성한다.
방별 즉시 admission과 전체 write budget은 최종에서도 유지된다. 유한 저장 대기 후보는 미채택.
응답 불명에 새 키를 만들지 않는다. Api.result/Store.result는 동일 키의 저장 결과를 조회한다.
브라우저 app.js는 전송 전에 IndexedDB pending에 key/body/hash를 저장한다.

[전달 실행기 → MySQL: 전달 작업 선점·본문 조회·완료]
Publisher.poll → Store.claim/publication/finish (기준).
최종은 claim/publications/finishBatch: 최대32개 작업의 UPDATE/본문 JOIN/완료를 묶는다.
claim은 FOR UPDATE SKIP LOCKED, 완료는 id+lease_token으로 fencing.
완료 기록은 로컬 publish 이후다. 소켓 수신이나 APPLIED 완료 기록이 아니다.
publish 후 DONE 전에 종료되면 재발행 가능. 만료 lease 재선점/재시도 및 poison 격리 유지.

[전달 실행기 → 연결별 전달: 방별 팬아웃]
Publisher.poll이 Gateway.publish를 직접 호출하고 routes[room]의 구독을 순회한다.
정상 연속 메시지는 issue로 즉시 전송 큐에 등록한다. DB가 소켓에 직접 push하지 않는다.
기준: credit 부족 시 Sub.buffer(TreeMap)와 globalBuffer 예산을 사용, 넘치면 buffer를 비우고 로그 복구.
최종: 수신자별 대기 본문 버퍼 없음. gap/credit 부족이면 공유 로그 조회에 맡긴다.
최종도 socket frames와 outstanding credit 원장은 유한하게 존재한다. '버퍼가 전혀 없음'이 아니다.

[연결별 전달 → 앱 메모리]
기준 Gateway.publish/drain/clearBuffer가 수신자별 live 버퍼를 보관·배출한다.
최종 Gateway.issue → WireCache.encode: messageId/hash가 같은 불변 JSON과 UTF-8 길이를 재사용.
구독 prefix는 Sub 생성 때 재사용 준비. 각 연결의 frame String 생성까지 없앤 것은 아니다.
캐시는 직렬화 표현만 보관한다. 권한·head/floor·조회 Page의 TTL 캐시가 아니다.
권한이 허용된 현재 DB 조회/발행 Message가 있어야 encode에 들어온다.
eviction/cold miss/동시 miss는 동기화된 encode에서 처리한다. 캐시 소실로 복구 로그가 없어지지 않는다.

[수신 브라우저 → 구독·복구: 연속 cursor로 재구독]
app.js localRoom/subscribe: IndexedDB 본문과 연속 cursor 및 로컬 generation 일치 확인.
Gateway.subscribe: 새 구독 객체·epoch, 인증 만료·closing·현재 구독 재확인 후 READY.
기준은 Store.history(...limit=0)에서 권한 SELECT와 head/floor SELECT 및 RR transaction 왕복.
최종은 Store.subscription → batchHistory(end=0): membership JOIN room 한 SELECT의 권위 snapshot.
원래 cursor가 floor-1 아래면 RESYNC_REQUIRED, head 위면 INVALID_CURSOR. 조용한 cursor 보정 없음.
초기 구독은 각 identity를 독립 확인한다. 초기 권한 조회를 서로 다른 사용자끼리 공유하지 않는다.

[구독·복구 → DB / 연결별 전달: 누락 조회와 연속 전송]
기준 Gateway.tickPeer/load → Store.history: 수신자별 RR 페이지, 주기적인 보충.
최종 Gateway.load → RoomReads.submit/dispatch/run → Store.batchHistory.
같은 방과 after/32 범위의 동시 대기를 닫힌 그룹으로 병합. 완료 snapshot을 미래 요청에 재사용하지 않는다.
권한·floor·head·본문을 하나의 SELECT로 읽고, 요청별 bound/limit/연속 행 수를 재검사한다.
추가 공유 대상은 이미 구독 권한을 얻은 고정 membership. 요청·callback에서 identity 만료와 구독 세대를 검사한다.
동적 멤버십 철회 보장을 새로 입증한 구조가 아니다.
head/목록의 독립 재검증은 계속 수행한다. 같은 user/목록 cursor의 동시 목록 조회도 병합한다.
읽기 그룹은 기존 2슬롯 내에서 대기 순서를 유지하고 목록/본문을 번갈아 처리한다.
제출/완료 알림을 합쳐 dispatcher를 깨우고, APPLIED 뒤 window 여유가 생기면 다음 로그 페이지를 보충한다.
READY 당시 고정 목표 H까지 연속 적용한 뒤 LIVE로 돌아온다. 새 head 관측이 미완료 고정 H를 이동시키지 않는다.
현재 신규 메시지는 gap을 넘지 못한다. 소켓 전송과 ACK는 live/복구가 공통 경로를 사용한다.

[연결별 전달 → 브라우저 / 적용 후 ACK → 연결별 전달]
기준 Gateway.issue는 수신자마다 전체 MESSAGE JSON을 직렬화, writer가 매 프레임 sendMessage.
최종 issue는 본문 표현 재사용, writer는 take+drainTo(7) 후 Tomcat batching API로 즉시 flushBatch.
writer는 peer monitor 밖에서 socket I/O 수행. 묶음 수집 timer나 worker/window 증설은 없다.
유한 count/byte credit, ACK timeout, blocked write watchdog/실제 close 경계를 유지한다.
UNSUBSCRIBE는 즉시 credit를 반환하지 않는다. RETIRING/순서 있는 종료 barrier/CLOSE_ACK 또는 종료 회수.
브라우저 receive → apply → IndexedDB messages/rooms/meta 단일 readwrite transaction 완료 후 APPLIED.
중복 id/hash 확인, seq=cursor+1, 오래된 connection/epoch 배제. 큐64 초과면 연결 종료 후 복구.
소켓 쓰기 성공 ≠ APPLIED. APPLIED ≠ 읽음. 읽음 버튼은 별도 Api.read/Store.read로 membership.read_seq를 단조 갱신.
읽음/목록/APPLIED의 보조 화살표는 그림 혼잡을 줄이기 위해 생략했다. APPLIED는 범례의 적용 후 ACK로 설명하며, 코드 추적에서는 확인했다.

[클라이언트 재접속 정책 — 서버 변경과 구분]
기준 브라우저: 250ms 지수 대기 +0~200ms jitter, OPEN에서 실패 횟수 초기화.
최종 app.js + retry-policy.js: READY가10초 안정 유지된 뒤 첫 종료에만25~325ms jitter.
실패/READY 전 종료/짧은 READY는500~1000 →1000~2000 →2000~4000 →2500~5000ms로 backoff.
OPEN만으로 실패 이력을 초기화하지 않는다. 실제 브라우저에 구현된 정책이다.
직전 k6의 legacy 재시도는100+index%500ms였으므로 k6 개선 폭을 실제 브라우저 사용자 개선 폭과 같다고 하지 않는다.
최종 k6는 같은 정책 바이트를 사용하되 고정 수신자 seed, 브라우저는 Math.random을 사용한다.

5. 관측 원인과 기능 검증을 구분
docs/articles/shared-fanout.html: 조회 증폭, Jackson JFR 표본, 고정 주기 dispatcher 대기/DB 실행 분리, live 직접 전달의 후속 도입.
docs/articles/mixed.html: 실제 JFR/SQL digest, 동일 복구량 통합 변경, 유한 저장 대기 미채택.
docs/articles/reconnect.html: 같은 메시지의 일부 수신자 지연, 2×2 대조 및 초기 구독 큐/쿼리 단계.
초기 대조는 타방만 재접속 효과 -0.0185%p, 자기 재접속 -1.5%p, 동시 복귀 추가 -0.7778%p(각1회).
이를 보편적인 '인기 방은 영향 없음' 또는 모든 원인이 클라이언트라는 결론으로 바꾸지 않았다.
실제 DB/프로세스/TCP 회귀: docs/causal-contracts.json의25사례.
최종 실제 브라우저: browser-reconnect-U-20261031-195206, browser-pending-20261031-195317.
IndexedDB 원자 abort/재시작/세대, 지속 단절 backoff, 응답 유실 후 같은 키 pending을 별도 검증했다.
이는 대규모 영속 적용 성능 수치가 아니다.

6. 문서·주석과 코드의 차이
shared-fanout.html의 초기 설명은 당시 RR transaction을 다룬다. 최종활성 batchHistory는 한 SELECT이므로 후자에 맞춰 그렸다.
최종 Gateway의 클래스 주석은 hint-triggered 로그 전달이라고 요약하지만, 실제 publish에는 연속 live 직접 issue 경로가 있다. 이를 그림에서 빠뜨리지 않았다.
기준도 routes 인덱스와 socket writer를 이미 사용한다. 이를 개선 후에 새로 만든 것처럼 표시하지 않았다.
최종 properties에 buffer-bytes가 남아 있어도 실제 Sub에는 live buffer가 없다. 캐시와 전송 큐로 구분했다.
초기 구독 최적화는 서버 Store.subscription, 재시도 정책은 실제 브라우저 retry-policy.js다.
문서의 '채택'은 조건부 일반 사용자 경험 개선이다. 전체 성능/복구 목표 통과가 아니다.

사용자 지정 시각 참고: https://github.com/jungjiyu/toss_mogu/tree/40f7c52662237bca09cc305dfa0c767d3320e647/docs/portfolio/architecture
before.mmd/after.mmd/layout.json/render.py/preview.html과 실제 after.svg를 확인했다.
같은 스타일의 고정 열, 회색 서버 경계, 흰 기능 상자, DB 원통, 직각 화살표와 초록 변경 경로를 적용했다.
해당 프로젝트의 코드·성과·아키텍처를 StoryBridge 근거로 재사용하지 않았다. 참고 저장소는 수정하지 않았다.
Mermaid11.12.0 공식 npm browser bundle로 두 .mmd를 실제 Chrome에서 구문 검증한다.
fixed_svg.py가 .mmd의 노드·라벨·화살표·변경 class를 읽고 layout.json의 공유 좌표로 SVG를 출력한다.
모구시장과 같은 방식으로 의미와 배치를 분리했다. Mermaid 자동 배치 결과를 그대로 저장한 SVG는 아니다.
노션에서 .mmd를 직접 렌더링하면 배치가 달라질 수 있다. 검수한 배치를 보존하려면 SVG를 사용한다.
발신자/수신자 왼쪽, 서버 중앙, MySQL 오른쪽. 두 그림의 모든 노드와 화살표 좌표는 동일하다.
DB 원통은 같은 트랜잭션에 포함되는 여러 테이블을 묶은 표현이며 하나의 물리 테이블을 뜻하지 않는다.
실시간/복구는 같은 writer를 사용한다. 메모리 점선 테두리는 프로세스 내부 유한 버퍼/캐시를 표시한다.
