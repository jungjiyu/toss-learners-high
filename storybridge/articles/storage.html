message·roomSeq·receipt·outbox의 원자적 저장과 응답 유실 처리

SEND 직후 연결이 끊기면 클라이언트는 저장 결과를 확인할 수 없으므로, 같은 요청을 재전송하더라도 메시지가 중복 저장되지 않도록 전송 키별 결과를 receipt에 기록했다. 메시지 본문과 함께 roomSeq, receipt, outbox를 commit하고, 이후 재시도에는 기존 결과를 반환한다.

방 행 잠금으로 순번 배정과 commit 순서를 직렬화했다. STORED는 commit 이후에 반환하며, 저장 이후의 발행 실패는 outbox 재처리로 복구한다. lease token을 완료 조건에 포함해 만료된 worker의 갱신도 차단했다.

저장·전송·수신 확인 단계

StoryBridge는 사용자 활동·콘텐츠·실시간 대화를 제공한 네트워킹 서비스다. 과거 서비스에는 Relay 채팅과 AI 피드백 기능이 있었으며, 이번에는 고정 구성원의 1:1·소규모 방을 대상으로 저장·전달·복구를 재구현했다. 여러 기기는 같은 DB 로그를 연속 cursor로 복구한다. AI·FCM·회원 트리·파일·검색·관리자 제품은 재구현 범위에서 제외했다.

메시지 처리는 저장·발행·전송·로컬 적용·읽음 단계로 나뉜다. MySQL commit, outbox 완료, WebSocket write, 클라이언트 commit, 읽음 상태는 각각 별도로 관리하며, 서버가 STORED를 반환했다면 서버 로그와 멱등 결과, 발행 의도가 같은 트랜잭션으로 남아 있어야 한다. 따라서 STORED는 수신자의 연결 상태와 무관한 저장 확인 응답이며, socket write 이후의 영속 적용은 별도 APPLIED로 확인한다.

기준과 개선 구현에는 같은 MySQL/InnoDB를 사용했다. 방별 잠금, consistent read, commit 내구성을 해당 버전에서 확인했으며, 서로 다른 DB 제품의 성능 차이를 개선 폭에 포함하지 않았다.

구현 조건: 같은 사용자·방·키와 같은 UTF-8 본문을 재전송하면 최초의 messageId·roomSeq·storedAt이 돌아온다. 같은 키의 다른 본문은 충돌이다. 응답을 잃었으면 같은 키로 결과를 조회하거나 재시도한다. 결과 불명을 새 전송으로 바꾸지 않는다.

roomSeq·receipt·outbox의 원자적 저장

사용자는 HMAC 서명과 만료를 검증한 token의 principal로 결정한다. SEND·결과·이력·bootstrap·읽음은 모두 고정 membership을 확인한다. 본문은 유효한 UTF-8 8KiB 이하이고, 멱등 키는 공백 없는 ASCII 1~64 자다. 본문 hash는 입력 문자열의 UTF-8 바이트에 대한 SHA-256 이다. NFC와 NFD를 임의로 합치지 않으며, 정규화 형태가 다르면 서로 다른 본문으로 판정한다.

최초 조회에서 receipt가 없었다는 이유로 바로 INSERT하면 동시 재시도가 서로 다른 효과를 만들 수 있으므로, room 행을 FOR UPDATE로 잠근 다음 receipt를 다시 확인한다. 방 행 잠금은 순번 배정과 commit 순서를 직렬화한다. receipt가 있으면 내용을 대조하고 최초 결과를 반환하고, 없으면 head+1 을 배정하여 message·receipt·outbox를 쓰고 room.head를 갱신한다. 전역 UUID와 시각, outbox AUTO_INCREMENT는 commit cursor로 사용하지 않는다.

// Serialize commit order. No AUTO_INCREMENT value is used as the room cursor.
                long head=jdbc.queryForObject("SELECT head FROM room WHERE id=? FOR UPDATE",Long.class,room);
                var existing=jdbc.query("SELECT * FROM send_receipt WHERE room_id=? AND sender_id=? AND client_key=?",RECEIPT,room,who.user(),key);
                if(!existing.isEmpty()) {
                    if(!existing.getFirst().hash().equals(digest))throw new Fault("KEY_CONFLICT",409);
                    metrics.inc("idempotent_replays");return existing.getFirst();
                }
                if(jdbc.queryForObject("SELECT COUNT(*) FROM outbox WHERE room_id=? AND state<>'DONE'",Long.class,room)>=2048)throw new Fault("OUTBOX_FULL",429);
                long seq=head+1,at=System.currentTimeMillis();String id=UUID.randomUUID().toString();
                jdbc.update("INSERT INTO message VALUES (?,?,?,?,?,?,?,?)",room,seq,id,who.user(),key,body,digest,at);
                jdbc.update("INSERT INTO send_receipt VALUES (?,?,?,?,?,?,?)",room,who.user(),key,id,seq,digest,at);
                jdbc.update("INSERT INTO outbox(room_id,seq) VALUES (?,?)",room,seq);
                jdbc.update("UPDATE room SET head=?,last_body=? WHERE id=?",seq,body,room);
                hooks.hit("send.before_commit");
                if(hooks.take("send.rollback"))throw new Fault("INJECTED_ROLLBACK",503);
                who.check();return new Receipt(room,who.user(),key,id,seq,digest,at);
            });

예를 들어 head=100 인 방에 K1 과 K2 가 동시에 도착하면 먼저 방 잠금을 얻은 트랜잭션만 101 을 배정한다. 그 트랜잭션이 rollback되면 head도 되돌아가므로 다음 성공이 101 을 쓴다. K1 의 응답만 사라졌다면 두 번째 K1 은 방 잠금 이후 receipt를 발견하고 같은 101 을 돌려준다. 다른 사용자의 동일 문자열 키는 별도 principal의 요청으로 취급하며, 결과 조회로 다른 사용자의 receipt를 읽을 수는 없다.

실제 MySQL 병렬 SEND 시험은 같은 키 8 회와 서로 다른 키 24 회를 구분했다. 같은 키는 중복 저장되지 않았고, 서로 다른 키의 commit 구간은 연속이었다. commit 직전 앱 프로세스를 종료한 경우 message·counter·receipt가 함께 사라졌고, commit 직후 응답 전에 종료한 경우 같은 키로 재시도하면 기존 seq가 반환됐다. 단순 예외 주입뿐 아니라 실제 JVM 종료를 함께 사용했다.

outbox 발행과 실패 재처리

메시지별 outbox는 메시지마다 한 개의 durable outbox 행을 남긴다. 단일 worker가 짧은 트랜잭션에서 최대 32 개를 SKIP LOCKED로 가져오고 lease token과 만료 시각을 기록한다. 실제 발행 후 완료 갱신은 id·LEASED 상태·lease token을 모두 조건으로 하므로 오래된 worker는 새 lease의 완료를 덮어쓸 수 없다. 여기서 SKIP LOCKED는 작업 경쟁용이며, 사용자 이력의 완전성을 판정하는 조회에는 사용하지 않는다.

단일 서버에서 발행은 같은 프로세스의 구독 인덱스로 전달하는 알림이다. 이미 DB에 저장된 본문을 로컬 route로 전달한 뒤 DONE을 기록하기 전에 실패하면 중복 힌트가 발생하지만, gateway의 연속 발행 원장과 수신자의 messageId/hash/cursor 대조가 중복 적용을 방지한다. 이 DONE은 broker confirm이나 consumer ACK, 수신 APPLIED를 뜻하지 않는다. broker confirm·ACK는 별도 RabbitMQ 구현에서 검증했다.

일시 오류는 유한 backoff로 재시도하며, 명시적 비호환 payload만 반복 실패 후 QUARANTINE으로 격리한다. 초기 구현에서는 모든 반복 오류가 격리될 수 있어 DB 일시 단절도 자동 복구를 멈출 위험이 있어 transient와 poison을 구분했다. E05 에서는 특정 메시지를 세 번 실패시켜 격리하고 다른 방의 발행 진전을 확인했다. 원본 행은 남았고 retention은 그 seq를 넘지 못했으며, 원인을 제거한 뒤 같은 의도를 재처리했다.

이력 조회와 retention의 snapshot 일관성

READ COMMITTED에서는 SELECT마다 snapshot이 달라질 수 있으므로, MySQL 기본 연결은 READ COMMITTED로 두되 이력 페이지는 별도의 read-only REPEATABLE READ 트랜잭션을 사용한다. 이 안에서 권한 확인, F/head 조회, 본문 조회가 같은 consistent-read snapshot에 속하도록 했다. 페이지 조회에는 consistent read만 사용하며 locking read를 혼용하지 않는다.

public Page history(Auth.Identity who,long room,long after,long requestedBound,int limit,boolean bootstrap) {
        if(after<0||requestedBound<0||limit<0||limit>64)throw Fault.invalid();
        return permit(reads,()->snapshot.execute(status->{
            authorize(who,room);
            var meta=jdbc.queryForMap("SELECT head,floor_seq FROM room WHERE id=?",room);
            long head=((Number)meta.get("head")).longValue(),floor=((Number)meta.get("floor_seq")).longValue();
            long base=bootstrap?Math.max(floor-1,head-limit):after;
            long bound=requestedBound==0?head:requestedBound;
            if(base<floor-1)throw new Fault("RESYNC_REQUIRED",409);
            if(base>head||bound>head||bound<base)throw new Fault("INVALID_CURSOR",409);
            hooks.hit("history.after_head");
            List<Message> messages=limit==0?List.of():jdbc.query("SELECT * FROM message WHERE room_id=? AND seq>? AND seq<=? ORDER BY seq LIMIT ?",MESSAGE,room,base,bound,limit);
            long expected=base+1;for(Message message:messages)if(message.seq()!=expected++)throw new Fault("LOG_GAP",503);
            if(limit>0&&messages.size()<Math.min((long)limit,bound-base))throw new Fault("LOG_GAP",503);
            metrics.inc("history_queries");metrics.add("history_rows",messages.size());who.check();
            return new Page(room,floor,head,bound,base,messages);
        }));
    }

retention은 room 행을 같은 순서로 잠그고, 미완료·격리 outbox가 참조하는 최소 seq를 보호하며, DONE 의도와 본문 삭제, floor 갱신을 한 트랜잭션에서 처리한다. receipt에는 본문으로의 삭제 cascade가 없으므로 본문 보관 기간이 끝난 후에도 과거 SEND의 결과를 확인할 수 있다. 보관 정책을 정기 실행하는 운영 scheduler는 이번 최소 제품에 포함하지 않았고, 시험용 보호된 endpoint와 실제 Store 연산으로 경계를 검증했다.

T42 는 F/head를 읽은 지점에 barrier를 걸고 다른 DB 연결에서 retention을 commit했다. 이미 열린 페이지는 삭제 전의 일관된 본문을 반환했고, 다음 페이지는 새 F를 보아 RESYNC_REQUIRED를 반환했다. 삭제와 floor 갱신 사이 rollback도 실제로 확인했다. C=F−1 은 유효하지만 C<F−1 은 과거 의무를 복구할 수 없는 상태다. bootstrap으로 새 B를 설정한 경우에도 보관 기간이 지난 이전 전달 의무는 복구 실패로 기록한다.

방별 admission과 DB 진입 제한

연결 풀을 늘리는 대신 DB 진입 전에 쓰기 6 개·읽기 4 개를 제한하고, 방별 진입은 257 개의 고정 stripe semaphore로 제한했다. 서로 다른 방이 같은 stripe에 매핑되면 경합에 의해 함께 거절될 수 있다. MySQL 잠금 대기 1 초, SQL timeout 3 초, 트랜잭션 timeout 4 초, Hikari 획득 500ms도 별도로 둔다. 거절은 BUSY/429 이고, transaction 시작·commit 결과가 불명인 DB 오류는 RESULT_UNKNOWN/503 이다.

외부 MySQL 연결이 한 방의 counter를 실제로 잠근 상태에서 8 개 수신자를 재접속시키고 정상 방에 SEND를 넣었다. 인기 방 요청은 제한 안에서 거절되고 정상 방 저장 및 오래된 수신 cursor가 모두 진전했다. 실제 mysqld를 종료한 시험은 Windows launcher PID와 실제 서버 PID가 다를 수 있음을 드러냈다. @@pid_file로 실제 서버를 식별한 뒤 kill했고, DB 재기동 후 동일 키 결과와 기존 WebSocket의 로그 복구를 확인했다.

실행 계획과 JFR 진단

최종 비교 후 동일 스키마에서 EXPLAIN ANALYZE와 DB 원장 대조, 실제 JVM Flight Recorder 10 초 기록을 별도 실행했다. 아래 화면은 실제 SQL 결과를 로컬 HTML 검수 화면으로 렌더링한 것이다. 앞선 benchmark 시점의 원래 화면이라고 표현하지 않는다. JFR 원본은 이 노트북의 .runtime/profiles에 유지하며 위치·hash와 추출 event는 진단 메타데이터에 있다.

응답 유실·동시 전송·보관 경합의 검증

필수 경계는 실제 MySQL, 실제 네트워크, 실제 SQLite/IndexedDB에서 실행했다. H2 나 mock의 성공으로 잠금·내구성을 대신하지 않았다. 합성 계정과 고정 권한만 지원하므로 동적 권한 철회·tombstone·replica lag는 해당 없음이다. flush_commit=1, sync_binlog=1 을 SQL로 확인했지만 물리 디스크 전원 차단·다중 장애 도메인의 quorum HA를 시험한 것은 아니다.

Flyway 11.7.2 는 MySQL 8.4 에 대한 검증 버전 경고를 출력했지만, 선택 스키마의 migrate·validate·반복 재기동은 실제 통과했다. 경고는 기록에 남겼으며 해당 버전에 대한 공급사의 공식 검증 여부는 별도다. 모든 전이 라이브러리는 gradle.lockfile과 각 실행의 environment.json에 고정했다.

모든 성공·실패 시험의 인덱스와 아래 비교 글의 적용 표에서 실제 실행을 확인할 수 있다. 초기 진단 실행은 일부 dirty/untracked 코드가 섞여 있었으므로 최종 측정의 재현 출처와 구분한다. 최종 benchmark는 소스·하네스 SHA, 개별 파일 hash, 실행 jar hash, 명령과 DB 감사 결과를 함께 보존했다.

공식 동작 근거: MySQL 8.4 consistent read, locking read와 SKIP LOCKED, Flyway MySQL 지원 설명. 실제 선택 버전의 경계는 위 재현 결과와 함께 판단했다.

과거 서비스 코드와 재구현 범위

제공 코드에는 인프로세스 SimpleBroker 설정과 애플리케이션의 전역 사용자 registry 순회가 있었다. 이 순회는 방 목록 알림 로직이며, SimpleBroker 내부의 비용이라고 단정할 수 없다. 저장과 방송이 같은 @Transactional 호출 안에 있어 DB commit 이전에 방송 경로가 실행될 가능성도 확인했다. 클라이언트 senderId를 신뢰하는 경로, 구독별 방 권한 확인의 부재, roomSeq·durable outbox·연속 로컬 cursor의 부재는 이번 계약에서 보완해야 하는 정적 위험이다.

과거 설명의 1,000 VU 및 CPU 81.4%→28.1% 수치는 과거 경험의 진술로, 당시 코드·원본 측정·컨테이너 조건이 이 실험에 제공된 것은 아니므로 이번 SimpleBroker 측정이나 이번 개선 폭으로 재사용하지 않았다. 이번 재구현의 버퍼 기반 기준부터 새 기준 코드이며, 아래 결과는 이 노트북에서 새로 실행한 것이다.

제약 사항

기준과 개선 구현 모두 MySQL/InnoDB를 사용했다. 과거 서비스의 STOMP Relay 전환 및 성능 측정은 이번 재구현과 별도다.
